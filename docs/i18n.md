# OS in four languages

OS is available in English, French, Spanish, and Italian, chosen under **Setup > Language** in the menu. English is the default and the fallback for every string a translation has not covered yet. Picking a language translates the OS menu, the Quickshell desktop, and its notifications, and sets the session's `LANG` to match, so other applications follow as they are opened: `LANG` goes to `~/.config/uwsm/env.d/50-arch-language`, which uwsm exports at every login, and into the running session. `uwsm app` runs an app in a scope, which keeps the environment of whatever launched it (Hyprland for bindings, the shell for the launcher), so the running session takes it in two steps: `hl.env("LANG", …, true)` sets it in Hyprland and passes it on to the systemd and D-Bus activation environments services start from, and the shell is then restarted from Hyprland to inherit it. Apps already open keep the language they started with until restarted, and the system locale in `/etc/locale.conf` (the console, the login screen) is left alone. A `LANG` the user sets in a later uwsm env file, or an `LC_ALL`, `LC_MESSAGES` or `LANGUAGE` they export, still takes precedence. The OS interface re-renders live from the language file, so the shell restart is only there to hand the new `LANG` to the apps it launches. The supported input-method setup covers the four listed languages; additional CJK locale choices are not exposed.

## Where things live

- `default/i18n/locales.json` — the four-language registry: code, native name, English name, BCP 47 format locale, and glibc locale.
- `default/i18n/en/menu.json`, `shell.json`, `cli.json` — the English source catalogs. Every other language mirrors their keys exactly in `default/i18n/<code>/`.
- `docs/user/*.md` — the English manual. Translations live in `docs/user/<code>/` under the same file names.
- `~/.config/arch/language` — the user's choice, one registry code. A missing or unknown code means English.
- `src/arch/commands/arch-language` — shows or sets the language and the session's `LANG`. With no argument it prints the current code; `list` prints the picker rows; `archctl language it` switches. Only generating a locale that isn't generated yet needs root, as one elevated script with a single password prompt: `sudo` in a terminal, `pkexec` when picked from the menu. Switching between generated locales prompts for nothing. The choice is persisted only after that succeeds, so a cancelled prompt leaves everything as it was.
- `default/i18n/<code>/keybindings.json` — the descriptions in the keybindings menu (Super+K), keyed by their English text. The English catalog is generated from the bind calls in `default/hypr/bindings/*.lua` by `scripts/i18n-sync.py` (a description built with `..` becomes a `%1` pattern such as `Switch to workspace %1`), and `arch-menu-keybindings` swaps each row's description for the current language's as it shows the menu, after ordering the rows in English. A description a user wrote shows as written.
- `src/arch/commands/arch-i18n` — prints one `cli.json` string in the current language: `arch-i18n battery.lowBody 12`. Catalog entries carry `%1`-style tokens, substituted from the extra arguments, so translations may reorder them freely.
- `src/arch/shell/Commons/I18n.qml` — the shell singleton. QML reads `I18n.t("common.search")` (or `Commons.I18n.t(...)` with a qualified import), with `.arg(...)` filling `%1` holes. It layers the current language's `shell.json` over the English one and re-renders live when the language file changes. It also exposes `formatLocale` from the registry. Shell code that prints day or month names formats with `Qt.locale(I18n.formatLocale)` rather than `Qt.formatDate` or a bare `Qt.locale()`, which follow the `LANG` the shell inherited rather than the language file. Qt's `MMMM` is the genitive month (right in "14 октября", wrong in a heading), so a month on its own uses `standaloneMonthName`, and date patterns that vary by language (`clock.dayMonthFormat`, `clock.monthYear`) live in the catalog.
- `src/arch/shell/plugins/menu/MenuModel.js` — `applyTranslations` retitles the shipped menu rows from `menu.json` before the user's menu extension merges on top, so user rows and retitles always win. The English label moves into the row's search-only terms, which keeps English search working in every language without making English words routable menu commands. The injected root row ("Go") has no JSONC entry, so its label comes from the catalog's `root` entry.
- `tests/shell.d/i18n-test.sh` — checks the four-language registry, English menu catalog freshness against `arch-menu.jsonc`, key and placeholder parity for French, Spanish, and Italian (structural by default, so manual chapters pending translation do not fail; `I18N_STRICT=1` also requires nothing pending), every catalog key referenced and every referenced key present, per-language manual structure, and `arch-language` / `arch-i18n` behavior against stubbed locale files.

## Adding or changing a string

English changes first, translations follow. For a menu label, edit `default/arch/arch-menu.jsonc` and mirror the change in `default/i18n/en/menu.json` (the test fails until they agree). For a shell string, add the key to `default/i18n/en/shell.json` and read it with `I18n.t(...)`; plain-JS models take an optional `tr(key, english)` argument defaulting to the English text, which the Node tests assert. For a notification or other user-facing CLI string, add the key to `default/i18n/en/cli.json` and print it with `arch-i18n`. Terminal output, usage text, and diagnostics stay English, as does the developer gallery; plugin manifest names and descriptions are not translated yet.

A few habits keep a translated string correct. Keep each sentence whole in one key with `%1`-style placeholders, never glued from translated pieces, since other languages reorder words; where English branches on a count, use a `…One` key for exactly one beside the general key. Translate at the point of display: a value that is stored, compared, or answered over IPC stays English, and a line that must keep an English literal carries an `// i18n: ignore` comment so the extractor passes it. Keep `I18n.t()` inside bindings so a language switch re-renders it; text assembled once when something happens keeps the old language until rebuilt. A QML `Text` whose text becomes an `I18n.t()` binding needs an explicit `textFormat` (`qml-text-format-test.sh`). Day and month names come from `Qt.locale(I18n.formatLocale)` (`standaloneMonthName` for a month on its own), never `Qt.formatDate` or a bare `Qt.locale()`; in `src/arch/commands/`, run `date` with `LC_TIME="$(arch-language locale)"`. Date patterns that vary by language, like `clock.dayMonthFormat`, live in the catalog as Qt patterns.

Third-party shell plugins ship their own catalogs and read them through `Commons.Translations` (`src/arch/shell/Commons/Translations.qml`), and Arch-style apps follow the language with a small JSON-backed `QTranslator`; the `arch` skill's `plugins.md` and the `arch-app` skill describe both for the agents that build them.

Until a translation catches up, the missing key simply renders in English. The site keeps its manual in English for now (`manual: false` in its registry); the translated manuals in this repo are ahead of it and can be picked up there later.

## Keeping translations in sync

Individual pull requests only ever add the English side: the string in code plus its English catalog entry (or the English manual chapter). The `i18n-check` workflow validates structure on pull requests — catalogs well-formed, placeholders intact, English menu catalog fresh, and no user-facing English literals embedded directly in `src/arch/commands/` or `src/arch/shell/` — but deliberately does not require translations. The extractor flags any QML property whose name ends like display text (`text`, `tooltipText`, `activeTooltipText`, `leftLabel`, `placeholderText`, …), every literal on such a line, and bare string-list items such as hero phrases; in `src/arch/commands/`, literals on `archctl notification send` and menu prompt lines. A handful of intentional literals (brand names and fixed phrases) live in `default/i18n/extract-allowlist.json`; for one line rather than one string everywhere, use the `// i18n: ignore` marker.

The `Sync translations` workflow does the converging, modeled on arch-site's translate workflow. It runs on pushes to `main` that touch English sources, daily, and on demand. `scripts/i18n-sync.py` computes what is pending from `default/i18n/translation-manifest.json`, which records the hash of the English source every catalog key and manual chapter was translated from; a unit is pending when its translation is missing or its English changed since. The workflow first extracts any English that was embedded directly in code — on a credential-less runner that only produces a patch, which another credential-less job applies and validates (the checks load the extracted code, so nothing there may hold a token), and a trusted job path-checks and publishes without running any repository code — then runs one credential-less Muse runner per pending language, collects and validates their patches under per-language path allowlists without credentials, updates the manifest, and lands everything through a final trusted job, again only git and gh, as a single pull request from the `i18n-sync` branch with auto-merge enabled, so it merges itself once `i18n-check` passes. The one exception: when extraction changed executable code under `src/arch/commands/` or `src/arch/shell/`, auto-merge is turned off, even if an earlier run enabled it, and the pull request waits for a human review. Failed languages simply stay pending and are retried on the next run; English is never blocked. The same script works locally: `python3 scripts/i18n-sync.py pending` shows the queue and `translate --locale es` fills one language.

Repository settings this needs: the `MUSE_API_KEY` Actions secret (optional `MUSE_MODEL` variable), an `I18N_SYNC_TOKEN` secret holding a fine-grained PAT with contents and pull-requests write on this repository (pull requests created with the default `GITHUB_TOKEN` do not trigger workflow runs, so their required check would never report; without the PAT the sync pull request still opens but needs a human nudge), "Allow auto-merge" enabled, and `i18n-check` as a required status check on `main` so auto-merge actually waits for validation.

## Translator brief

Translate like the interface was written in your language: short, natural, and in the register of consumer desktop software. Menu labels are one or two words where the language allows it. Keep the following exactly as they are: product and brand names (Arch, Hyprland, Neovim, Chromium, application names, agent names, font names), technical tokens (DNS, DHCP, AUR, TUI, VM, QR, GPU, SSH, PATH), commands, file paths, URLs, keyboard key names (Super, Alt, Ctrl, Home, F9), and placeholders (`%1`, `%2`, … in both catalogs) — a translation must carry the same placeholders as its English source, though it may reorder them. Clock-format preview labels translate the weekday and month words only; times and digits stay. ALL-CAPS section headers stay capitalized where that is natural for the script. In the manual, preserve Markdown structure, headings, links, code blocks, commands, and file names verbatim, translate link text and prose, and keep the author's voice — the manual is opinionated on purpose.

Regional note: `es` is Spanish for Spain. The system's Italian keyboard layout remains an independent keyboard setting and does not restrict the chosen display language.

A plural entry is an object of CLDR categories rather than a string: English writes `{"one": "%1 device", "other": "%1 devices"}`, and each translation supplies exactly the categories its language's counts reach — Russian `one`, `few`, `many`, `other`; Arabic all six; Japanese only `other` — always keeping every placeholder in `other`, and dropping the count from a form only where the language says the number with a word.

## Plurals, numbers, and direction

Plural rules live twice, in `src/arch/shell/Commons/Plural.js` for the shell and `default/i18n/plural.jq` for `arch-i18n`, and `i18n-test.sh` checks the two agree for every language. The sync script asks `plural.jq` which categories a language needs, so translations come back complete. In QML, `I18n.tn("key", count)` picks the form (`.arg()` still fills the holes); in bash, `arch-i18n --count "$n" key "$n"`; a plain-JS model takes an optional `tn` the way it takes `tr`. A string that only abbreviates a unit (`%1h`, `%1 min`) is not a plural.

Numbers follow the language too: the registry's `decimal` and `zeroDigit` (taken from Qt, so they match the dates it writes) give Italian `13,1` and Persian `۱۳٫۵`. Shell code formats displayed numbers with `I18n.formatNumber(value, decimals)` (`src/arch/shell/Commons/Numbers.js`), never `toFixed` or `toLocaleString`; `arch-i18n` localizes any argument that is a plain number, so commands pass numbers as their own arguments with the unit in the catalog string, and `arch-i18n --number` writes one number for text outside a catalog. Numbers are not grouped, so a year or a port never grows a separator.

The supported languages use left-to-right writing direction. Their date and number formats come from the locale registry and are verified by `i18n-test.sh`.
